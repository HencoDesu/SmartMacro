# PerfectWorldAgent — Техническое описание

> Версия: 0.4  
> Статус: Рабочая версия, активная разработка

---

## 1. Обзор проекта

Агент для автоматизации управления отрядом персонажей в MMORPG Perfect World.  
Снимает с игрока ручную работу по вводу персонажей в игру и синхронизации действий вспомогательных персонажей в данжах: автологин всех окон, идентификация персонажей по классу, широковещательные команды (иммунка, ассист, макросы, клики) на все окна одним хоткеем.

От ранних версий спеки (0.3 и ниже) отказались от: режимов FOLLOW/HOLD/COMBAT со стейтмашиной оркестратора, детекта застревания, LLM-интеграции (Ollama/Claude), ростера персонажей с per-character конфигом, идентификации по нику. Причины — по ходу документа.

---

## 2. Состав отряда

- **10–11 персонажей**, каждый в отдельном процессе `elementclient_64.exe`
- **1 главный (мастер)** — управляется игроком вручную; в конфиге задаётся классом (`MasterClass`, по умолчанию Лучник)
- **Остальные** — управляются агентом
- **Персонаж-склад** — заведён в игру, но игнорирует все команды (`IgnoredClasses`, по умолчанию Шаман)

Идентичность персонажа = его **класс** (все классы в отряде уникальны). Ники персонажей могут совпадать — это не мешает. Отдельного ростера нет: все клиенты настроены одинаково, общие бинды берутся из `AgentOptions` (`DefaultImmunityKey`, `DefaultAssistKey`).

## 3. Контекст игрового процесса

### Особенности клиента PW

- **Движок замораживает неактивные окна** — ввод и рендеринг фоновых клиентов стоят. Любая операция с фоновым окном требует пробуждения через `WM_ACTIVATEAPP` с магическим lParam (см. раздел 6).
- **Клиент запускается elevated через UAC.** Из-за UIPI ввод и захват экрана от менее привилегированного процесса блокируются/обрезаются, поэтому агент тоже запускается от администратора (`requireAdministrator` в манифесте).
- **Модификаторы не работают через message-инъекцию.** PW читает состояние Shift/Ctrl через `GetKeyState`, которое cross-thread `SendMessage`/`PostMessage` не обновляют. Chord'ы вроде Shift+1 в фоновое окно невозможны — вместо них клики по UI (выбор мастера в отряде = клик по слоту 1 party-панели).
- Все окна клиента имеют одинаковый заголовок и имя процесса — различить их можно только визуально.
- Клики мышью через `PostMessage` работают надёжно; клавиатура надёжна только через `SendMessage` (синхронная доставка в WndProc).

### Типовой сценарий работы

```
Игрок запускает 10-11 клиентов PW
    → Агент видит процессы, для каждого запускает boot-flow:
        ждать экран выбора сервера (vision) → клик "Войти"
        → ждать экран выбора персонажа (vision) → клик "Войти в игру"
        → ждать появления игрового UI (vision)
        → открыть окно статов (C) → распознать класс → закрыть статы
    → Все окна идентифицированы, иконки классов на таскбаре
    → В данже игрок管ит мастером и жмёт хоткеи:
        иммунка на всех / взять ассист / запустить макрос / клик по курсору на всех
```

## 4. Стек технологий

| Компонент | Технология |
|---|---|
| Язык / runtime | C# / .NET 10 (`net10.0-windows`) |
| UI | Avalonia 11 |
| WinAPI | P/Invoke через `LibraryImport` (source-generated); отдельный проект `PerfectWorldAgent.Native` |
| Vision (шаблоны UI, класс персонажа) | OpenCvSharp — template matching (`TM_CCOEFF_NORMED`) |
| OCR координат | Tesseract — **законсервирован** (в DI, но не используется; пригодится для будущего детекта застревания) |
| Скриншоты | `PrintWindow` (`PW_CLIENTONLY \| PW_RENDERFULLCONTENT`) + System.Drawing |
| Сериализация | System.Text.Json (полиморфизм через `[JsonPolymorphic]` для действий макросов) |
| State machine агента | Stateless (два состояния: `AwaitingIdentification` → `Idle`) |
| DI / Configuration / Hosting | Microsoft.Extensions.* (HostApplicationBuilder) |
| Логирование | Serilog (Console + File с роллингом), source-generated `[LoggerMessage]` |

LLM-интеграции нет. Все решения детерминированные: vision + конфиг.

## 5. Архитектура

Три проекта со строгой слоистостью: `App` (Avalonia UI, composition root) → `Core` (домен) → `Native` (Win32, без зависимостей).

```
Orchestrator (диспетчер, IHostedService)
    ├── ProcessMonitor        — полинг процессов игры (события ProcessAppeared)
    ├── HotkeyListener        — глобальные хоткеи (RegisterHotKey + WH_MOUSE_LL)
    └── CharacterAgent × N    — по одному на процесс игры
            ├── IGameWindow           — ввод + захват + WaitForElementAt (vision-примитив)
            ├── AgentInputDispatcher  — activate → send → deactivate вокруг каждого ввода
            ├── ICharacterProvider    — идентификация класса по окну статов
            └── MacroRunner           — исполнение макросов
```

### Orchestrator

Чистый диспетчер — **никакой стейтмашины режимов**. Маршрутизирует:

- `HotkeyListener.HotkeyPressed(trigger)` → broadcast соответствующего `AgentMessage` во все инбоксы агентов
- `HotkeyListener.MacroHotkeyPressed(имя)` → `BroadcastMacro(имя)` → `RunMacroMessage`
- `ProcessMonitor.ProcessAppeared` → создание агента через `CharacterAgentFactory`
- Upstream от агентов (identified / stopping) — через общий `Channel<AgentMessage>` inbox + dispatch loop

Триггеры хоткеев (`OrchestratorTrigger`): `BroadcastImmunity`, `BroadcastAssist`, `BroadcastClick`, `BroadcastDoubleClick`, `BroadcastIdentify`.

### CharacterAgent

Один агент = одно окно игры. Стейтмашина минимальная: `AwaitingIdentification → (Identified) → Idle`. Макросы и broadcast-команды выполняются из `Idle` fire-and-forget, без переходов состояний.

Жизненный цикл:
1. **Создание** — при появлении процесса. Процессы с нулевой client-area (лаунчеры) отфильтровываются.
2. **Boot-flow** (`EnterWorldAsync`, автоматически на старте) — vision-управляемые фазы: ждать шаблон экрана сервера → клик по координатам кнопки → ждать шаблон экрана персонажа → клик → ждать шаблон игрового UI. Каждая фаза — `IGameWindow.WaitForElementAt(шаблон, регион, таймаут)`. Если клиент уже в игре (рестарт агента) — фазы пропускаются по быстрой проверке InWorld-шаблона.
3. **Идентификация** (`IdentifyAsync`) — открыть статы (клавиша C), passive-захват, `ClassMatcher` сматчит текст класса в фиксированном регионе против шаблонов `Assets/GameClassNames/{Класс}.png`, закрыть статы. Успех → `Character { Name = класс, Class = класс }`, иконка класса на таскбар, переход в `Idle`.
4. **Работа** — обработка инбокс-сообщений (см. ниже).

Однополётность: `SemaphoreSlim(1,1)` (`_operationLock`) на boot/identify/macro-run — конкурентный триггер той же операции превращается в no-op (`WaitAsync(0)`).

Ручной оверрайд: если авто-идентификация не сработала, оператор назначает класс агенту прямо из главного окна (dropdown + Assign) — минуя vision полностью.

### Сообщения (broadcast-команды)

| Сообщение | Действие агента |
|---|---|
| `UseImmunityMessage` | Нажать `DefaultImmunityKey` |
| `TakeAssistMessage` | Клик по слоту 1 party-панели (выбрать мастера) → нажать `DefaultAssistKey` (in-game макрос /assist). Мастер пропускает |
| `RunMacroMessage(имя)` | Найти макрос в библиотеке, взять действия ДЛЯ СВОЕГО КЛАССА, исполнить через MacroRunner |
| `ClickAtMessage(точка, dbl)` | Клик/даблклик по client-координатам (курсорный broadcast) |
| `EnterIdentifyMessage` | Запустить идентификацию (только если ещё не идентифицирован) |

Неидентифицированные агенты глотают все команды кроме identify. Классы из `IgnoredClasses` (склад) глотают вообще все.

### Макросы

```csharp
Macro {
    Name,
    ActionsByClass: Dictionary<CharacterClass, List<MacroAction>>
}
MacroAction = KeyPressAction(клавиша) | DelayAction(мс) | ClickAction(точка, dbl)
```

- **Per-class действия**: у каждого класса свои скиллы и кастование — один broadcast, каждый агент исполняет свой блок. Класс без блока = no-op.
- **Редактор** (Macros dialog): панели классов, типизированные строки действий (пикер клавиши / задержка в секундах / координаты клика), перестановка ↑↓, кнопка Run (broadcast прямо из редактора).
- **Хоткеи на макросы**: динамический список в Settings (имя макроса + сочетание). `HotkeyListener` маршрутизирует по id либо в триггер, либо в имя макроса.
- **Персист**: `macros.json` рядом с exe. FileSystemWatcher hot-reload при внешнем редактировании (свои записи подавляются по LastWriteTime, debounce 300мс).

### Vision

Единый примитив: `IGameWindow.WaitForElementAt(byte[] шаблон, ScreenRect регион, TimeSpan бюджет)` — poll-цикл (500мс): активный захват (разбудить → PrintWindow → заморозить обратно) → grayscale → `Cv2.MatchTemplate(TM_CCOEFF_NORMED)` → скор против порога.

- **Grayscale, не бинаризация** — элементы UI лежат на полупрозрачных фонах, где бинаризация нестабильна из-за просвечивающего мира. `TM_CCOEFF` сам нормализует яркость.
- Исключение — `ClassMatcher` (текст класса на непрозрачной панели статов): там бинаризация по luminance даёт чистый матч (скор 1.000).
- Шаблоны: `Assets/GameUiElements/*.png` (ключ = имя файла, ссылки по имени из `AgentOptions`) и `Assets/GameClassNames/{Класс}.png`. Копируются в output при сборке.
- Пустой регион (`Width=0`) = поиск по всему кадру. Регионы заданы для скорости и защиты от ложных матчей.
- ⚠️ Все координаты и шаблоны сейчас привязаны к разрешению 3840×2160 автора. Масштабирование под другие разрешения — в бэклоге.

### Ввод (выстрадано практикой — не менять без ре-теста на живой игре)

Каждый ввод обёрнут в activation-lifecycle (`AgentInputDispatcher`):

```
ActivateAsync   — SendMessage(WM_ACTIVATEAPP, магический lParam) + settle-задержка
    → ввод (клавиши / клики / чтение)
DeactivateAsync — drain-задержка + деактивация (если окно не в фокусе игрока)
```

| Канал | Метод | Почему |
|---|---|---|
| Клавиатура | `SendMessage` | PostMessage-клавиши терялись в замороженной очереди (1-2 из 9 окон случайно) |
| Мышь | `PostMessage` | Клики доходят всегда, блокирующий Send не нужен |
| Иконка окна (`WM_SETICON`) | `SendMessage` + ретраи 2с/5с | Post висел в очереди фоновых окон; PW при автовходе может сбросить иконку своей инициализацией |
| Chord'ы (Shift+X) | ❌ невозможны | `GetKeyState` не видит инъецированные модификаторы — заменено кликами по UI |

### Конфигурация

1. **`appsettings.json`** — секции `Serilog`, `Agent` (процесс, бинды, мастер-класс, кнопки boot-flow, шаблоны), `Input:Activating` (тайминги активации, слот мастера), `Vision:ClassMatcher` / `Vision:Window` (регионы, пороги). Биндится однократно через `IOptions` — изменения требуют перезапуска.
2. **`appsettings.local.json`** — опциональные локальные оверрайды (gitignore).
3. **Runtime-конфиги рядом с exe** (gitignore, редактируются из UI без перезапуска):
   - `hotkeys.json` — бинды триггеров + бинды макросов (`HotkeyConfigStore`: immutable snapshot → `ReplaceAsync` → событие → live-перерегистрация)
   - `macros.json` — библиотека макросов (`MacroLibrary`, тот же паттерн + hot-reload)

Подбор координат: навести курсор в игре → хоткей BroadcastClick/DoubleClick → в логе client-координаты точки → перенести в конфиг. Подбор регионов vision: кнопка "Dump captures" пишет `debug/*-full.png` и `*-class-bin.png` на каждого агента.

## 6. Управление (Stream Deck / хоткеи)

Stream Deck шлёт глобальные хоткеи (F13–F24 — не конфликтуют с игрой). Регистрация: `Win32HotkeyMonitor` (RegisterHotKey, клавиатура) + `Win32MouseHookMonitor` (WH_MOUSE_LL, кнопки мыши). Бинды редактируются в Settings dialog, на время диалога регистрация приостанавливается (иначе занятые сочетания не перехватить в пикер).

Дефолтные бинды (сидируются при отсутствии `hotkeys.json`):

| Хоткей | Триггер |
|---|---|
| F23 | Иммунка на всех |
| F22 | Клик по курсору на всех |
| F21 | Даблклик по курсору на всех |
| F20 | Идентифицировать неопознанных |
| — | Ассист (назначается вручную) |
| настраиваемые | Хоткеи макросов (имя → сочетание) |

## 7. UI (Avalonia)

- **Главное окно** — список живых агентов (имя, состояние, идентифицирован ли), для неопознанных — dropdown класса + Assign. Кнопки: Dump captures (отладка vision), Macros, Settings. Закрытие окна сворачивает в трей; выход только через трей-меню.
- **Macros dialog** — редактор макросов (см. раздел 5), кнопка Run на каждом макросе.
- **Settings dialog** — бинды встроенных триггеров + динамические бинды макросов.
- Иконки классов на таскбаре игровых окон (`Assets/ClassIcons/*.png`, маппинг русских имён классов на английские файлы в `ClassIconService`) — чтобы различать 10 одинаковых окон PW.

## 8. Законсервировано / вне скоупа

**Законсервировано в коде** (работает, но не подключено):
- `TesseractCoordinateReader` — OCR координат из UI. Зарегистрирован в DI, потребителей нет. Пригодится для будущего детекта застревания. Отлаживается через `tools/VisionSampleRunner`.

**Вне скоупа текущей версии:**
- Режимы FOLLOW/HOLD и автоматизация движения отряда (привязка/отвязка)
- Детект застревания и дерево восстановления
- LLM-анализ нештатных ситуаций
- Отслеживание кулдаунов, механики боссов
- Чтение памяти процесса игры
- Автоперезапуск вылетевших клиентов (игрок запускает сам — агент подхватит и введёт в игру)

**Бэклог (активный):**
- Масштабирование шаблонов и регионов под произвольные разрешения экрана (сейчас — только 4K автора)

## 9. История ключевых решений

| Решение | Было (spec 0.3) | Стало | Почему |
|---|---|---|---|
| Идентификация | Template matching ника на HUD | Класс из окна статов | Игрок сделал всем персонажам одинаковые ники; классы уникальны; шаблон класса — один на класс, а не на персонажа |
| Конфиг персонажей | Ростер с per-character биндами | Класс = идентичность, общие дефолтные бинды | Все клиенты настроены одинаково — ростер был лишней сущностью |
| Режимы оркестратора | Стейтмашина FOLLOW/HOLD/COMBAT | Убраны, чистый диспетчер broadcast'ов | Реальный workflow — игрок сам решает когда что жать; автоматизация режимов не окупилась |
| Бой | Два прохода бурста с фикс. клавишами | Библиотека макросов с per-class действиями | Гибкость: разные ротации, разные тайминги кастов по классам |
| Ассист | Shift+1 (выбор мастера) + клавиша | Клик по слоту 1 party-панели + клавиша | Модификаторы не доставляются в фоновые окна (GetKeyState) |
| Ввод в игру | Игрок сам логинит все окна | Автоматический boot-flow по vision-фазам | Рутина на 10+ окон; фикс. задержки не работали — скорость загрузки непредсказуема |
| LLM | Ollama + Claude fallback | Убрано | Не осталось задач: всё покрыто детерминированным vision + конфигом |
