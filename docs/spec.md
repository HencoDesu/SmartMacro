# PerfectWorldAgent — Техническое задание

> Версия: 0.3 (draft)  
> Статус: В разработке

---

## 1. Обзор проекта

Агент для автоматизации управления отрядом персонажей в MMORPG Perfect World.  
Цель — снять с игрока ручную работу по синхронизации действий вспомогательных персонажей во время прохождения данжей, оптимизировать тайминг бурст-окна и надёжно обрабатывать нештатные ситуации (застревание персонажей).

---

## 2. Состав отряда

- **10 персонажей** суммарно
- **1 главный** — управляется игроком вручную (окно Win+1)
- **9 вспомогательных** — управляются агентом (окна Win+2 … Win+10)
- **1 тестовый аккаунт (11-й)** — для безопасного тестирования механик агента

Каждый персонаж запущен в отдельном процессе игрового клиента.

Главный персонаж в архитектуре агента представлен как `CharacterAgent[1]` с флагом `IsMaster=true`. Он не получает команд (FOLLOW/COMBAT), используется только для пассивного мониторинга координат — по его движению определяется, должен ли двигаться остальной отряд. В будущих итерациях функционал главного агента может расширяться.

---

## 3. Контекст игрового процесса

### Типовой цикл данжа

```
Отряд движется к боссу (режим FOLLOW)
    → Игрок останавливает отряд перед боссом (режим HOLD)
    → Игрок даёт сигнал к бою (режим COMBAT)
        → Проход 1: бурст-бафы на урон (не начинают бой)
        → Проход 2: дебафы + скиллы урона (начинают бой)
    → Босс умирает за 5–10 секунд
    → Отряд движется к следующему боссу (режим FOLLOW)
```

### Особенности

- Большинство боссов умирает в течение одного бурст-окна
- Внутриигровые макросы на персонажах уже настроены
- Перемещение между боссами через механику "Следовать" (привязка)
- Привязка активируется двойным кликом по имени главного персонажа в интерфейсе отряда
- Отвязка — любой шаг персонажем в произвольную сторону
- Движок игры замораживает неактивные окна (отключается через внутриигровую консоль)
- Клиент игры запускается **elevated через UAC**. Из-за UIPI любой ввод (PostMessage / SendInput) и захват экрана (PrintWindow) от менее привилегированного процесса в его окно — либо блокируется, либо обрезается. Поэтому агент сам должен запускаться от администратора (`requireAdministrator` в манифесте `PerfectWorldAgent.App`)

## 5. Архитектура

### Структура агентов

```
Orchestrator
    ├── ProcessMonitor
    ├── CharacterAgent[1]  (IsMaster=true — только мониторинг координат)
    ├── CharacterAgent[2]
    ├── CharacterAgent[3]
    ├── ...
    └── CharacterAgent[10]
```

**Orchestrator** — центральный координатор:
- Получает сигналы со стримдека (хоткеи)
- Переключает режимы (FOLLOW / HOLD / COMBAT) через стейтмашину на библиотеке Stateless
- Координирует CharacterAgent-ов через очереди сообщений
- Получает уведомления от агентов ("персонаж застрял")
- Обращается к LLM при нештатных ситуациях

Стейтмашина: триггеры `GoFollow / GoHold / GoCombat / CombatFinished / Stop`. Поверхность оркестратора разделена на два слоя:

- **Сообщения от агентов — через очередь.** Один shared `Channel<AgentMessage>`, write-side выставлен как `Orchestrator.Inbox`. `CharacterAgent` пишут туда `StatusUpdateMessage`, `StuckDetectedMessage`, `ConnectionLostMessage`. Фоновый dispatch loop (`IHostedService`) дрейнит inbox через `WaitToReadAsync` и маршрутизирует по типу. `ConnectionLostMessage` автоматически вызывает `UnregisterAgent(id)` — вылет процесса не требует ручного вмешательства. Очередь нужна потому что агентов много, события случаются плотно, recovery-логика (LLM, retry attempts) может быть тяжёлой.
- **HotkeyListener и ProcessMonitor — события, на которые подписывается оркестратор.** Оба — пассивные observer'ы (ОС-процессов и клавиатуры соответственно), их задача только заметить и сообщить. Они выставляют события (`HotkeyPressed`, `ProcessAppeared`, `ProcessDisappeared`); оркестратор подписывается в своём конструкторе и отписывается на `Dispose`. UI или другие диагностические потребители могут подписаться независимо. Обработчики выполняются на потоке источника (message loop у хоткея, polling thread у монитора) — Orchestrator.OnHotkeyPressed блокирующе ждёт `FireAsync().GetAwaiter().GetResult()`, конкурентные вызовы `FireAsync` сериализуются через `SemaphoreSlim` (Stateless не thread-safe).
- **Downstream (оркестратор → агенты).** При переходе оркестратор пишет `ModeChangedMessage` во все зарегистрированные инбоксы агентов (`ChannelWriter<AgentMessage>`). Реестр — `ConcurrentDictionary<string, ChannelWriter<AgentMessage>>`, заполняется через `RegisterAgent(id, inbox)` после создания каждого `CharacterAgent` (в перспективе — самим оркестратором в обработчике `OnProcessAppeared`).

`Orchestrator` зарегистрирован одним singleton'ом, и тот же инстанс отдан как `IHostedService` для управления dispatch-loop жизненным циклом:

```csharp
services.AddSingleton<Orchestrator>();
services.AddHostedService(sp => sp.GetRequiredService<Orchestrator>());
```

Никакого `IOrchestrator` интерфейса нет — продьюсеры (HotkeyListener, ProcessMonitor) ничего у оркестратора не запрашивают, они выставляют события и оркестратор подписывается на них. Будущий UI и `CharacterAgent` зависят на конкретный класс (UI читает `Mode` / `ModeChanged` / `FireAsync`; агенты получают `ChannelWriter<AgentMessage>` через `Orchestrator.Inbox`). Если потом понадобится мокать оркестратор для UI-тестов — введём интерфейс под конкретный use case.

Host сам зовёт `StartAsync` при `host.StartAsync()` и `StopAsync` при `host.StopAsync()` в `Program.Main`. Тесты гоняют upstream детерминированно через `ProcessIncomingAsync()` без запуска фоновой петли.

Для UI выставлено лёгкое sync-событие `event Action<AgentMode>? ModeChanged` — поток обновляет привязки в UI без async-церемонии. UI обычно сам инициирует смену состояния через `FireAsync`, событие нужно для случаев когда состояние меняется внутри (`CombatFinished`).

Актуальная диаграмма автоматически генерируется в [docs/state-diagram.mmd](state-diagram.mmd) при прогоне тестов.

**ProcessMonitor** — фоновый компонент, отслеживает запущенные процессы игрового клиента полингом `Process.GetProcessesByName` с диффом множеств PID. Интервал настраивается, по умолчанию 1 секунда. При обнаружении изменений **поднимает события** `ProcessAppeared(ProcessInfo)` / `ProcessDisappeared(int pid)`. Сам монитор не знает кто слушает — это pure observer; оркестратор подписывается в своём конструкторе. Поведение проверяется интеграционным тестом на реальном Notepad, тест подписывается на события напрямую. Мок-абстракции над `Process.GetProcessesByName` намеренно нет (одна продакшен-реализация, шум без выгоды).

Никаких событий и публичного API сверх `IHostedService` — единственный наблюдаемый эффект монитора это сообщения в оркестраторе. Это даёт **оркестратору единоличное владение жизненным циклом агентов**: получив `ProcessAppearedMessage`, он сам идентифицирует персонажа (template matching), создаёт `CharacterAgent`, вызывает `RegisterAgent`; на `ProcessDisappearedMessage` чистит соответствующую регистрацию. ProcessMonitor не знает что такое CharacterAgent — он только смотрит на ОС.

Параметры (имя процесса, интервал опроса, эндпойнт Ollama и т. п.) собраны в `AgentOptions` и биндятся из секции `Agent` в `appsettings.json` через `services.Configure<AgentOptions>(...)`. ProcessMonitor получает `IOptions<AgentOptions>` в конструкторе.

DI:

```csharp
services.Configure<AgentOptions>(configuration.GetSection("Agent"));
services.AddSingleton<ProcessMonitor>(sp => new ProcessMonitor(
    sp.GetRequiredService<IOptions<AgentOptions>>(),
    sp.GetRequiredService<Orchestrator>().Inbox,
    sp.GetRequiredService<ILogger<ProcessMonitor>>()));
services.AddHostedService(sp => sp.GetRequiredService<ProcessMonitor>());
```

Тест на Notepad использует тот же публичный конструктор через `Options.Create(new AgentOptions { GameProcessName = "notepad", PollIntervalSeconds = 1 })` — лишний `internal` ctor не нужен. Лимит 5 секунд на ожидание сообщения с запасом покрывает спавн Notepad + один тик опроса.

**CharacterAgent** — управляет одним окном через абстракцию `IGameWindow` (см. ниже):
- Работает с `IGameWindow` вместо сырого hwnd — вся работа с окном (ввод, скриншоты) скрыта за обёрткой
- Читает OCR своих координат
- Детектирует своё застревание (только для `IsMaster=false`)
- Исполняет команды оркестратора (только для `IsMaster=false`)
- Отправляет статус оркестратору

**IGameWindow** — обёртка над окном игрового клиента. Хранит hwnd, делегирует ввод выбранной реализации `IInputSender`, делает скриншоты через `WindowCapture`. Конкретный `GameWindow` композируется из `(hwnd, IInputSender)` на этапе подключения процесса, после чего `CharacterAgent` не зависит ни от выбора стратегии ввода, ни от деталей P/Invoke. В тестах легко мокается.

**WindowCapture** — статический хелпер, делает screenshot client-area окна через `PrintWindow` с флагами `PW_CLIENTONLY | PW_RENDERFULLCONTENT`. Второй флаг важен для DirectX/DirectComposition окон (игровой клиент именно такой) — без него возвращается чёрный кадр. Размер берётся из `GetClientRect`, рисуется в `Bitmap(width, height, Format32bppArgb)` через `Graphics.GetHdc()`, кодируется в PNG `byte[]` через `Bitmap.Save(..., ImageFormat.Png)`. Поскольку клиент PW запущен elevated, агент тоже должен быть elevated — иначе PrintWindow вернёт пустое изображение (см. раздел 3 про UAC).

### Взаимодействие

Агенты общаются с оркестратором через `System.Threading.Channels` (`Channel<T>`) — асинхронные очереди сообщений. Это позволяет агентам работать параллельно и уведомлять оркестратора без блокировок.

### Последовательность подключения окна

Все окна игрового клиента имеют одинаковое имя процесса и одинаковый заголовок, поэтому идентификация делается визуально с последующим переименованием окна для уникальности:

```
ProcessMonitor видит новый процесс игры
    → Снять скриншот окна (PrintWindow)
    → Идентифицировать имя персонажа (template matching по эталонным изображениям)
    → Найти персонажа в конфиге, определить роль (IsMaster или нет)
    → Отключить заморозку неактивного окна (внутриигровая консоль)
    → Переименовать заголовок окна для уникальной идентификации (внутриигровая консоль)
    → Создать CharacterAgent с привязкой к hwnd
```

Конкретные консольные команды (отключение заморозки, переименование) — деталь реализации, уточняется при первом подключении.

### Конфигурация

Загрузка через `Microsoft.Extensions.Configuration` в `Program.cs`:

1. **`appsettings.json`** — рядом с exe, копируется в output, обязательный. Содержит блоки `Serilog` (sinks, уровни логирования) и `Agent` (имя процесса игры, эндпойнт Ollama, интервалы)
2. **`appsettings.local.json`** — опциональный, в `.gitignore`. Локальные оверрайды поверх основного конфига
3. **Переменные окружения** с префиксом `PWAGENT_` — оверрайды для CI / переменных
4. **Конфиг персонажей** (`AgentConfig` / `Characters`) — пока отдельный JSON в `config/`, в перспективе мигрируется в `appsettings.json` или остаётся отдельным файлом ради удобной правки игроком

### Логирование

Serilog через `Microsoft.Extensions.Logging`. Конфигурация целиком в `appsettings.json` (`Serilog` секция). По умолчанию: консольный sink + файл `logs/pwagent-YYYY-MM-DD.log` с роллингом по дням, retention 14 дней, `Enrich.FromLogContext` для контекстных тегов. Bootstrap-логгер создаётся до построения хоста чтобы ошибки старта тоже попадали в файл.

### DI

`Microsoft.Extensions.DependencyInjection` через `HostApplicationBuilder`. Контейнер собирается в `Program.cs`, после чего `IServiceProvider` отдаётся в Avalonia `App` для резолва `MainWindow`. Все компоненты (Orchestrator, ProcessMonitor, ILanguageModel, IInputSender и т. д.) регистрируются как singleton/transient в `ConfigureServices`.

`PerfectWorldAgent.Native` — отдельный проект-обёртка над Win32 API. Группировка по абстракциям, не по DLL: публичная поверхность это `IKeyboardInput` / `IMouseInput` (service-style, принимают hwnd как параметр) + `INativeWindow` (per-hwnd инстанс, инкапсулирует Handle внутри, методы без hwnd-параметра) + `INativeWindowSystem` (фабрика INativeWindow + системные запросы GetForeground/GetScreenSize) + enum'ы (`VirtualKey`, `HotkeyModifiers`) и Hotkey-инфраструктура (`Win32HotkeyMonitor`). Конкретные impls (`PostMessageKeyboardInput`, `SendInputMouseInput`, и т.п.) каждая знает СВОЮ часть P/Invoke — общие декларации лежат в `Internal/User32Native.cs` (`internal static partial class`, `LibraryImport` source-gen). Core зависит от Native; больше нигде в проекте `[DllImport]`/`[LibraryImport]` нет.

`LibraryImport` source generator требует `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>` и явный `EntryPoint = "...W"` для функций с A/W вариантами (`PostMessage`, `SendMessage`, `GetMessage`, `PostThreadMessage`, `MapVirtualKey`) — это плата за AOT-готовый source-gen вместо рантайм-маршаллинга `DllImport`.

В DI зарегистрированы дефолты — `PostMessageKeyboardInput`/`PostMessageMouseInput`, обёрнутые в `ActivatingKeyboardInput`/`ActivatingMouseInput` (для PW-окон с заморозкой). Замена на `SendInput`-варианты — одна строка в `ConfigureServices`.

## 6. Режимы работы агента

### FOLLOW
- Персонажи следуют за главным через привязку
- Детектор застревания **активен**
- Агент периодически проверяет координаты всех персонажей

### HOLD
- Персонажи стоят на месте перед боссом
- Детектор застревания **отключён**
- Агент ничего не делает, ждёт сигнала

### COMBAT
- Агент выполняет два прохода активации
- Детектор застревания **отключён**
- После завершения — ждёт сигнала FOLLOW

## 7. Частота тиков агента

Разные задачи агента работают с разной частотой — нет единого цикла для всего.

| Задача | Частота | Примечание |
|---|---|---|
| Детект застревания | раз в 2-3 сек | Погрешность ±10м делает более частую проверку бессмысленной |
| OCR координат | раз в 2-3 сек | Совмещён с детектом застревания |
| COMBAT активация | разово по сигналу | Не цикличная, два прохода по окнам |
| LLM анализ скриншота | по необходимости | Только при нештатной ситуации |

Такой подход минимизирует нагрузку — основная постоянная работа это OCR 9 окон раз в 2-3 секунды.

## 8. Управление (Stream Deck)

Сигналы от игрока передаются через Stream Deck в виде глобальных хоткеев. Регистрация и обработка — `HotkeyListener` (`IHostedService`): на своём фоновом потоке вызывает `RegisterHotKey` для каждого биндинга из `HotkeyOptions`, крутит `GetMessage`-петлю, на `WM_HOTKEY` **поднимает событие** `HotkeyPressed(OrchestratorTrigger)`. Кто подписан — не его дело; оркестратор подписывается в своём конструкторе и в обработчике дёргает `FireAsync(trigger)` блокирующе. State machine сериализует concurrent FireAsync через `SemaphoreSlim`.

Биндинги настраиваются в секции `Hotkeys` `appsettings.json`. Дефолты: `Ctrl+Shift+F1..F4` → `GoFollow / GoHold / GoCombat / Stop`. `Ctrl+Shift+F*` редко используется в PW, проще подменить чем чистые F1-F4.

### Предварительная раскладка

| Кнопка | Хоткей | Действие |
|---|---|---|
| FOLLOW | F1 | Активировать привязку на всех, включить детект застревания |
| HOLD | F2 | Отвязать всех персонажей (шаг в сторону), выключить детект |
| COMBAT | F3 | Запустить два прохода активации |
| STOP | F4 | Экстренная остановка: режим → HOLD, отмена текущего COMBAT-прохода, очистка очередей `Channel<T>` |

> ⚠️ Раскладка предварительная, уточняется после практических тестов

### Ручное управление отдельными персонажами

Отдельные кнопки на стримдеке для ручной активации привязки/отвязки конкретного персонажа — на случай когда автоматика не справилась.

## 9. Логика боя (режим COMBAT)

Каждый бурст-проход — это нажатие **одной клавиши** на персонаже, которая запускает внутриигровой макрос с цепочкой скиллов. Проходы используют **две разные клавиши** (баф-макрос и урон-макрос) с паузой между ними.

```
Сигнал COMBAT получен
    → Проход 1 по окнам Win+2 … Win+10
        → Нажать клавишу бурст-бафа на каждом персонаже
    → Пауза (ГКД, точная величина уточняется в тестах)
    → Проход 2 по окнам Win+2 … Win+10
        → Нажать клавишу дебафа/скилла урона на каждом персонаже
```

### Метод ввода

Стратегии ввода реализованы в `Core/Input/` под общим интерфейсом `IInputSender`, рабочая выбирается по результатам тестов на живой игре:

- **PostMessage** (приоритет) — асинхронный, фоновый, не требует фокуса
- **SendMessage** — синхронный аналог
- **SendInput** — системная инжекция (DirectInput / Raw Input), требует фокуса. Переключение делается через `SetForegroundWindow` + `AttachThreadInput` как fallback
- **Декоратор активации** — посылает `WM_ACTIVATEAPP` перед каждым вводом, разбудит "замороженное" фоновое окно PW. Композируется поверх любой базовой стратегии

Альтернативный путь — отключить заморозку неактивных окон один раз через внутриигровую консоль при подключении (раздел 3). Какая комбинация выстреливает на PW — выясняется при первом доступе к игре.

## 10. Логика движения (режим FOLLOW)

### Детектирование застревания

- OCR координат из игрового UI (Tesseract)
- Формат координат: `X Z Y`, разделитель — пробел, целые числа
- Координаты постоянно видны в UI игры
- Расположение элементов интерфейса унифицировано для всех персонажей
- Погрешность ±10м достаточна для детекта факта "стоит/движется"
- Проверка каждые N секунд (уточняется в тестах)
- Персонаж считается застрявшим если **главный персонаж движется** (по координатам `CharacterAgent[1]`), а координаты подопечного не изменились за T секунд

### Отдельные случаи (не "застрял")

- **Смерть в городе** — персонаж умер и воскрес в городе. Координаты резко изменились в локацию города. Обрабатывается отдельной логикой, не как застревание.
- **Вылет процесса** — игра нестабильна, вылеты случаются регулярно. Не считается ошибкой агента: ProcessMonitor удаляет соответствующий `CharacterAgent`, при повторном запуске процесса игроком — подключается заново.

### Дерево решений при застревании

```
Персонаж не движется
    → Попытка 1: переактивировать привязку
    → Всё ещё стоит?
        → Попытка 2: прыжок (Space) + переактивировать привязку
        → Повторить до N раз
        → Всё ещё стоит?
            → Уведомить игрока (звук + индикатор в UI)
            → Ждать ручного вмешательства
```

## 11. Роль LLM

LLM используется только для нештатных ситуаций которые не покрываются детерминированной локальной логикой. Базовые операции (OCR, детект застревания, ввод команд) выполняются локально без обращения к модели.

### Стратегия использования

- **Локальная модель (приоритет)** — Ollama или llama.cpp, работает на RTX 4080
- **Claude API (fallback)** — если локальная модель не справилась или недоступна
- Переключение прозрачное через интерфейс `ILanguageModel`

### Потенциальные задачи для LLM
- Анализ скриншота при нештатной ситуации
- Принятие решения в неоднозначных случаях застревания
- Расширенная логика боя в будущих версиях (кулдауны, приоритеты целей)

### Требования к локальной модели
- Поддержка vision (анализ скриншотов) — **обязательно**
- Подходящие варианты: LLaVA, Llama 3.2 Vision, Qwen2.5-VL
- Уточняется после проверки что именно установлено дома

### Тест 2: PrintWindow
